# Purchase management

A standalone GRAIL world demonstrating a purchasing request from retrieval through human review, processing, and recording. Uses `@mamund/grail` **0.2.0** and three bindings: HTTP, Node, and interactive STDIO.

## Scenario

An employee has submitted a request for a replacement workstation. A purchasing service holds the request. A policy checker provides guidance; a human reviewer decides whether to **approve**, **reject**, or **defer** it. The purchasing system processes the decision and records the result.

**Goal:** `purchaseRecorded` (defined in `config/goal.json`). The goal is achieved when the purchasing service records the processed result. A deferred purchase is still a completed review and a successfully recorded outcome; the underlying purchase remains pending follow-up.

The default request is `P1042`, an Engineering workstation costing $2,450. A second sample, `P1043`, is a $125.50 office-supplies request. All data is fictional.

### Responsibilities and effects

| Affordance | Preconditions | Effect | Binding |
| --- | --- | --- | --- |
| `loadPurchaseRequest` | none | `purchaseLoaded` | HTTP GET |
| `checkPurchasePolicy` | `purchaseLoaded` | `policyChecked` | Node |
| `reviewPurchase` | `purchaseLoaded`, `policyChecked` | `purchaseReviewed` | Interactive STDIO |
| `processPurchase` | `purchaseReviewed` | `purchaseProcessed` | Node |
| `recordPurchaseResult` | `purchaseProcessed` | `purchaseRecorded` | HTTP POST |

The registry describes conditions and effects, not a fixed execution script. GRAIL discovers the required affordances from the goal. Domain decisions are handled inside capabilities.

### Domain outcomes

| Human decision | Processing action | Recorded domain status |
| --- | --- | --- |
| Approve | Create a simulated purchase order | `approved` |
| Reject | Close the request as rejected | `rejected` |
| Defer | Mark for follow-up | `deferred` |

All three decisions satisfy `purchaseReviewed`. After processing and recording, all three can satisfy `purchaseRecorded`. No actual purchase orders, notifications, or payments are issued.

## Requirements

- Node.js 22 or later
- A terminal that supports interactive input
- GRAIL v0.2.0, installed by `npm install`
- Port `3002` available on localhost

## Run

In the world directory:

```sh
npm install
npm run validate
npm run reset
```

Start the mock purchasing HTTP service in **terminal 1**:

```sh
npm run service
```

Run the goal in **terminal 2** (an interactive terminal):

```sh
npm start
```

At the review prompt, choose `1` (approve), `2` (reject), or `3` (defer), then enter an optional note. The expected result is `reached: true` for `purchaseRecorded`.

Inspect `data/state.json` to see the persisted review, processing status, and recorded result. Inspect `config/observations.json` if generated by your CLI for invocation evidence.

To run a different sample purchase, reset the domain store and override the input:

```sh
npm run reset
npx grail run --config ./config --inputs '{"purchaseId":"P1043"}' --output=json
```

For a fresh run, use `npm run reset` before starting GRAIL. The CLI resets GRAIL world state per run; `npm run reset` separately resets the mock purchasing domain store.

## What to observe

1. GRAIL pursues `purchaseRecorded`, resolving unmet conditions until the review can execute.
2. HTTP retrieves the request, Node checks policy, and interactive STDIO obtains the human determination.
3. The reviewer writes `review.status` to the domain store. GRAIL records the effect `purchaseReviewed`, without creating separate `purchaseApproved`, `purchaseRejected`, or `purchaseDeferred` conditions.
4. Node processes the stored outcome. HTTP records the processed result and establishes the final effect `purchaseRecorded`.
5. Captured outputs (such as `purchaseId` and `policyGuidance`) are available to downstream capabilities through `$outputs.latest.*`.

```text
├── capabilities/    # Node policy/processing, interactive review, domain store

```

## Design boundary

GRAIL world state contains boolean conditions indicating completed responsibilities. The domain store contains the actual purchase request, policy guidance, review status, and processing record. A successful review means a valid determination was made and persisted, including **deferred**. `processPurchase` treats deferred as a valid disposition by recording follow-up pending; it does not claim the purchase itself was fulfilled.

This is a teaching example, not a production purchasing system. Its JSON file store assumes a single local run, no concurrent writers, and no authorization or audit controls. The HTTP service is deliberately local-only.
